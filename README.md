# Mealio

Mobile-first, single-owner meal tracker. Planning and visual references stay in the parent `plan/` directory outside this Git repository.

**Status:** a Vercel/Neon smoke deployment passed owner login and logout; the private dashboard, authentication, migrations, and meal APIs passed local PostgreSQL/browser checks with dummy credentials. Live Fireworks interpretation, USDA lookup using a private key, and opt-in local INDB file/database lookups have been verified. The production INDB catalog, backups and device-level verification remain outstanding. `/preview` contains sample data only in development (404 in production) and is not private meal history. Do not use the deployment for real meal history until the remaining release checks pass.

## Local development

Use Node 20.11+ and PostgreSQL. Copy `.env.example` to `.env.local` and provide private values for `DATABASE_URL` and `FIREWORKS_API_KEY`. For USDA, the server reads `USDA_API_KEY` from the environment first; if unset or empty, it reads `../.secrets/usda_api.txt` at runtime. The file may contain a raw key or one `USDA_API_KEY=...` line. Set `USDA_KEY_FILE` if the file lives elsewhere. Keep the file outside the repo with owner-only permissions; set a private `USDA_API_KEY` environment value in deployment instead. Next loads `.env.local` for the web app; the migration and provisioning CLIs require `DATABASE_URL` in their own process environment. Do not commit credentials. Run `npm install`, `npm run db:migrate` with `DATABASE_URL` set, then `npm run dev`. Privately set `ADMIN_USERNAME`, `ADMIN_PASSWORD`, and `ADMIN_TIMEZONE` (IANA name) and run `npm run provision-admin` once with `DATABASE_URL` set. Provisioning refuses existing accounts; do not put these values in shell history or commit them. No signup endpoint exists.

Private recovery: in an authorized environment set `DATABASE_URL`, the existing `ADMIN_USERNAME`, and a new `ADMIN_NEW_PASSWORD`, then run `npm run recover-admin`. This rotates the password and invalidates all existing sessions atomically. There is no public reset endpoint. Never paste credentials into a committed file.

### Optional Indian recipe catalog

`dataset/` is ignored by Git and the staged-secret hook blocks accidental additions. The owner-provided `Anuvaad_INDB_2024.11.xlsx` stays local; **no INDB nutrient data is bundled, committed, or loaded by default**. Run `python3 scripts/prepare-indb.py` to audit it locally (requires `openpyxl` installed in your Python environment). The audit reports incomplete and unusual serving entries without rewriting the workbook. An incomplete serving is omitted from the private catalog while its per-100g values remain available for a known weight.

The owner approved using the INDB workbook for this private app. The INDB [portal](https://www.anuvaad.org.in/indian-nutrient-databank/) calls it open-access, but a bulk-redistribution licence for a **public Git repo** has not been established. Never commit the workbook or derived catalog. A private JSON catalog is prepared with `python3 scripts/prepare-indb.py --export dataset/indb-private.json --confirm-rights` and explicitly activated by setting server-side `INDB_DATA_FILE` to its absolute path (for local development, in ignored `.env.local`). The local demo has been tested with INDB recipe candidates through estimate, save, history and delete; production activation requires separate verification. The app accepts only unambiguous exact dish names (including qualified parenthetical aliases) with known weights or compatible servings; counted named foods such as roti and counted pieces of an exact burfi recipe are supported. Generic sweets and missing portions stay manual until specified rather than assuming a serving. All INDB candidates display recipe/portion uncertainty, and saved nutrition remains a snapshot.

For serverless production, the catalog must live in the private PostgreSQL database rather than the deployment filesystem. After backing up the production database, apply the additive `indb_catalogs` migration with `npm run db:migrate` using the **direct** database URL supplied privately to your local process. Inspect the private JSON export locally, then run `npm run import-indb -- --confirm-private-upload` with the same private direct `DATABASE_URL`. The importer reads only `dataset/indb-private.json`, validates the entire catalog and refuses an existing row; replacement requires the separate `--replace` flag. It never prints values or connection details. After verifying the import and deploying the code, set Vercel's **Production-only** `INDB_CATALOG_SOURCE=database` and redeploy. Do not set `INDB_DATA_FILE` on Vercel, paste the catalog into environment variables, or share the database URL. Without the database flag, production remains on USDA/manual fallback; local file mode continues to work.

Checks: `npm run lint`, `npm run typecheck`, `npm test`, and `npm run build`. Focus one test with `npx vitest run path/to/file.test.ts`.

The Fireworks coding-worker MCP server is configured in `opencode.json`; it reads its credential from `../.secrets/fw_api.txt` at runtime (or a path supplied via `FIREWORKS_KEY_FILE`). It returns proposed patches and never edits this checkout.
